# Back Recorder

Android background audio recorder with Google Drive sync and in-app billing.

Kotlin 17 · Jetpack Compose/M3 · Hilt (KSP) · Room · DataStore · WorkManager · Play Billing · Google Drive API · Gradle version catalog (`gradle/libs.versions.toml`) · Tests: JUnit 4, MockK, Turbine, Espresso, Compose UI test (instrumented)

Single `:app` module. Package root: `com.backrecorderapp`.

## Key Concepts

- **Segments:** Recordings are composed of segments — recording can be interrupted and resumed.
- **Recording state:** `RecordingService` exposes static `isRunning: StateFlow<Boolean>`. UI observes this directly — no DataStore pref. `AppPreferences.wasRecordingBeforeShutdown` is only for crash-recovery restart.
- **Segment flushing:** `SaveRecordingUseCase` → `RecordingFlusher.flushCurrentSegment()` finalizes the in-progress segment (writes MP4 MOOV atom) for `MediaExtractor`. Flusher is a Hilt interface backed by `RecordingService.flushCurrentSegment()` (static). Rotation guarded by `Mutex`.
- **Service teardown and rotation (#48):** four rules the recording loop depends on, none of them obvious from the code alone. (1) **`onDestroy` never blocks.** It cannot join the rotation — it runs on the main thread, a cancelled rotation cannot abandon a native muxer call part-way, and a join measured in seconds is what the foreground-service timeout and the ANR watchdog count against (observed: a 3 s join produced `ForegroundServiceDidNotStartInTimeException`). Instead `destroyed` and `audioRecorder` are both `@Volatile` and each side writes its own before reading the other's — `onDestroy` sets `destroyed` then reads `audioRecorder`, `startNewSegment` publishes the recorder then re-reads `destroyed` — so at least one of them stops a recorder opened during teardown. Keep that write-then-read order on both sides or the orphan comes back. (2) **The rotation loop catches its own errors**, `CancellationException` rethrown first (it extends `IllegalStateException`, so a bare `catch (e: Exception)` swallows teardown). One IO or database error used to cancel `rotationJob` silently for the rest of the session. The subtle part: `rotateSegment` stops the recorder *before* the waveform write, finalize and prune, so a throw in that stretch must not skip the reopen — it is held in a local and rethrown only after `startNewSegment()`/`startAmplitudeCapture()` have run. Skipping the reopen leaves the service alive, holding the wake lock and the notification, capturing **nothing** until the next tick; rethrowing matters too, or a flush whose finalize failed reports success and `SaveRecordingUseCase` proceeds on a segment that was never completed. `amplitudeBuffer` is drained and cleared by each rotation, capped as a backstop, and every access goes through `withAmplitudeBuffer` — `onDestroy` cannot join the amplitude coroutine, so a lock is the only thing covering that path. (3) **A recorder that will not start is fatal**, not logged: `startNewSegment` discards the row and file it reserved and throws `SegmentStartException`, and the loop and the flush collector stop the service rather than write an empty segment a minute behind a notification claiming to record. The stop waits `FOREGROUND_SETTLE_MS` first — leaving the foreground within milliseconds of entering it gets the process killed — and uses `stopSelf(startId)` so a recording the user begins during that settle is not torn down. It also abandons outstanding flushes, clears `wasRecordingBeforeShutdown` (so crash recovery does not restart a session that just failed the same way) and posts a notification on the recovery channel: a service that disappears silently leaves someone who started a background recording hours ago to find out from an empty save. (4) **`amplitudeJob` is cancelled *and joined*** before `rotateSegment` reads the buffer; cancellation alone is a request, and the old comment calling it safe was wrong.
- **Starting and stopping (#61, #62):** `onStartCommand` is idempotent. `startForeground` runs on *every* start, redelivered `START_STICKY` intents included — a start that returns without reaching the foreground is killed with `ForegroundServiceDidNotStartInTimeException` — and the `recordingStarted` guard sits immediately after it, so a double tap or `BootReceiver` racing an app start no longer opens a second recorder over the live one (orphaning the first, microphone and all) or overwrites `rotationJob`/`flushJob` with a second set. `stopBecauseRecordingFailed` clears that guard, because `stopSelf(startId)` is a no-op once a newer start has landed and a service left with the guard set would stay alive, in the foreground, recording nothing, with the UI's toggle unable to recover it. Stopping also **closes the segment that was open**: `closeOpenSegment()` hands the work to an injected `@ApplicationScope` scope (`onDestroy` cannot block and `serviceScope` is cancelled on the way out) and `closeCurrentSegment()` claims it under `rotationMutex`, so it is closed exactly once and never interleaves with a rotation. A segment with bytes on disk is finalized; one with a zero-length file is `discardSegment`ed, because a finalized row is a claim that `filePath` holds readable audio and `getSegmentsInRange` would hand that claim to every save. Every write of `currentSegment` is under that same mutex for the same reason — including the first one, in `startRecordingLoop`. Leaving the segment open was one orphan row plus its `.m4a` and `.bin` per session, permanently: `pruneOldSegments` only deletes complete rows, and `getSegmentsInRange` matches `isComplete = 0` forever.
- **Flush handshake:** the request/serve handshake lives in `FlushCoordinator` (`service/`), a static field of `RecordingService`'s companion. Requests go through an **unlimited `Channel`**, never a `SharedFlow` — a channel buffers with no receiver, so a flush asked for in the window between `_isRunning` flipping true and `flushJob` starting is queued rather than dropped. `onDestroy` calls `abandonAll(FlushAbandonedException())` *before* cancelling the jobs, so queued and in-flight requests fail instead of hanging. Because the coordinator is process-global it also enforces the inverse. It carries an `Epoch` (id + accepting): `abandonAll` bumps it and stops accepting, `reopen` — called from `onStartCommand`, **not** from the collector, or window 1 would reject requests for every session after the first — bumps it and accepts again, and `requestFlush` compares the epoch after enqueueing, so a request racing teardown (or teardown *and* restart, which a plain boolean would flip back) fails fast instead of being stranded for the next service instance. A caller that gives up cancels its own deferred so the collector skips it rather than rotating a later recording for a save that already failed. `SaveRecordingUseCase` additionally wraps the call in `withTimeout(FLUSH_TIMEOUT_MS)` and maps a timeout to `SaveResult.Error`, which `MainViewModel` surfaces as a retryable error and which deletes the empty SAF file. Three layers, all deliberate (#47): never drop, never abandon, never wait forever.
- **Recorder seam:** `RecordingService` records through `AudioRecorderFactory` / `AudioRecorder` (`service/recorder/`), not `MediaRecorder` directly. Production binds `MediaRecorderAudioRecorderFactory` in `di/RecorderModule` — same MPEG-4/AAC 16 kHz mono 32 kbps configuration as before. Instrumented tests replace *only* that module via `@TestInstallIn(replaces = [RecorderModule::class])` with `FakeAudioRecorderFactory`, whose `FakeAudioRecorder` encodes a synthetic tone through `MediaCodec` + `MediaMuxer`, so segments are real MP4s with a MOOV atom that `MediaExtractor` reads. A recorder instance is single-use: one `start()`, one `stop()`, one per segment. Inside `MediaRecorderAudioRecorder`, `PlatformRecorder` holds every `MediaRecorder` call and no decisions, so the release ordering (#48) is unit-testable on the JVM, where `MediaRecorder` cannot be constructed. The recorder field is guarded by one monitor taken by `start()`, `stop()` **and** `maxAmplitude()` — neither `@Volatile` nor an `AtomicReference` is enough, because `onDestroy` and a rotation can both reach `stop()` (a read-then-clear lets both release the same native recorder) and because an amplitude read that loads the reference and then calls through it in two steps can have the release land in between. The cost is that an amplitude read blocks for the length of one `MediaRecorder.stop()`, once per segment, which is the right trade against a native use-after-release. `stop()` may throw and releases regardless; `maxAmplitude()` reads 0 from the moment teardown begins. `FakeAudioRecorder` honours that contract too, but answers from a `@Volatile` flag rather than its encode lock — holding that lock would park the service's amplitude coroutine for a whole `feed()` and starve `Dispatchers.Default`, which is two threads wide on a CI emulator.
- **Minute-snapped selection:** Waveform *drag handles* snap to minute boundaries (start floors, end ceils). End handle clamps to `bufferEndTime` so the currently-recording minute stays reachable. Time-preset chips do **not** snap — they select an exact duration from the recording edge (#21).
- **WaveformView touch:** Custom `awaitEachGesture` pointer-input loop (not `detectHorizontalDragGestures`). Dedicated handle zones above/below waveform; 2D distance disambiguates overlapping handles.
- **Billing:** `BillingRepository` reports subscription status (FREE/ACTIVE); the money is taken by Play, not in-app. The app's only write is `launchPurchaseFlow`, which puts the user in front of Play's purchase sheet.
- **The upgrade hand-off (#72):** `launchPurchaseFlow` is **suspend and answers its caller** — null when the sheet was shown, a `PurchaseFailure` when it was not — rather than publishing on a shared flow. That shape is the fix, not an accident: both `MainViewModel` and `SettingsViewModel` offer the upgrade, and `MainViewModel` stays alive in the nav back stack while settings is on top, so a broadcast refusal in settings also latched an error on the main screen that fired whenever the user next went back. A per-call answer reaches only the screen that asked. The failure is the *user-visible* half; the response code and debug message go to logcat under the `PlayBilling` tag. Six things keep a hand-off from going quiet, which is the whole defect the issue reported. (1) A `Mutex` **serializes** hand-offs rather than dropping them — two overlapping attempts would open two connections on the one client, which Play answers with an error, but a *dropped* second tap is just as bad, because the second caller is usually the other screen and would be left with nothing to show. (2) One shared `CompletableDeferred` per connection attempt, so a purchase started while the app-launch `connect()` is still connecting waits for that attempt instead of issuing a second `startConnection` — otherwise an Upgrade tap in the first seconds after launch reports "unavailable" over a connection that succeeds a moment later. (3) `withTimeoutOrNull` bounds **only** connecting and querying, and the block it wraps returns a non-null `Prepared`: wrapping the launch too would cancel after Play had already shown the sheet, and returning a bare nullable made "timed out" and "the sheet opened" the same value — that conflation shipped a version where *every successful purchase* reported a failure, which is what the unit tests now pin. (4) `onBillingServiceDisconnected` answers the pending request, since the service can die while setup is still pending and the setup callback then never arrives. (5) Everything is wrapped in a `try`/`catch` returning `LAUNCH_FAILED` (rethrowing `CancellationException`), because a throw out of the Play client would otherwise reach `viewModelScope` and take the app down. (6) A `SERVICE_DISCONNECTED`/`SERVICE_UNAVAILABLE` product query **reconnects and asks once more** (`OfferQuery.Failed.retryable`), because the binding can drop between the `isReady` check and the query — the client reports ready right up to the moment it dies, so no check closes that window; `ITEM_UNAVAILABLE` is deliberately *not* retryable, since Play not having the product is not transient. `launchBillingFlow` itself must run on the main thread — off it Play returns `DEVELOPER_ERROR` and shows nothing — and the activity is re-checked for `isFinishing`/`isDestroyed` first, because preparing crosses a callback and the screen may be gone by then. Only `ITEM_UNAVAILABLE` or an OK-but-empty product list means `PRODUCT_UNAVAILABLE` (a Play Console problem: no such product, no active offer on the base plan, an account not on a buying track); every other response code is `BILLING_UNAVAILABLE`, because telling a tester their product is misconfigured when the network dropped sends them to fix the wrong thing.
- **Choosing the plan (#74):** the subscription is `main_subscription` — not `premium`, which is what the app asked Play for until #74 and which does not exist, so every Upgrade tap came back `ITEM_UNAVAILABLE`. **No test can catch a drift in that string**: every test fakes billing, and the only authority on it is the Play Console. It carries two base plans, `monthly` and `yearly`, each with a free-trial offer, which is why correcting the id alone would have been worse than leaving it broken — the hand-off took `subscriptionOfferDetails.firstOrNull()`, an ordering Play does not contract, so one tap would have charged an **arbitrary** plan, possibly a year the user never chose. So `loadSubscriptionPlans()` is a separate call from `launchPurchaseFlow(activity, plan)`, and the plan is required rather than defaulted: there is no fallback that is not an arbitrary charge. Offers are matched by `basePlanId` (via `BillingPeriod`, which owns those two strings) and **never by position**; within a base plan the trial offer wins, and no eligibility check is needed because `queryProductDetailsAsync` already returns only the offers this account can take. Prices are Play's own `formattedPrice` from `pricingPhases` — the recurring phase, not the free one in front of it — and are never assembled by hand, because a locale's separator, symbol and symbol position are not ours to guess; `priceAmountMicros` exists for arithmetic only. The yearly saving is **computed** (yearly vs monthly × 12) rather than written into the app: the ratio is a Play Console decision that can change without a release, so a hard-coded "17%" would become a lie in the UI, and the badge is hidden outright when the figure would mislead — one plan only, two currencies, or a yearly price that is not actually cheaper. The purchase re-resolves the offer from a fresh query rather than carrying the chooser's token, because the token and the `ProductDetails` handed to `launchBillingFlow` must come from the same response and the chooser's may be minutes old — so what crosses that gap is the *identity* of what the user picked (base plan **and** `offerId`, since a base plan may carry several eligible offers and "whichever came first" is the same ordering this change refuses to trust), with the preference rule only as a fallback and a vanished base plan failing closed. `loadSubscriptionPlans()` takes the same `purchaseMutex` and `PREPARE_TIMEOUT_MS` and maps a timeout or a throw to `BILLING_UNAVAILABLE`; unlike the hand-off its timeout wraps the **lock** as well, which is safe only because nothing user-visible has been launched yet — wrapping the launch that way is what #72 forbids. The chooser's selection is `rememberSaveable`: orientation cannot be restricted at this target on large screens, and a rotation that silently reverted the selection to the default would buy a year the user did not pick. Three things keep the chooser from latching, all of them the #72 defect in a new place: dismissing the upgrade offer **cancels the load it started** (otherwise the chooser arrives seconds after the user said no); `MainViewModel` outlives its screen, so `MainScreen` calls `onScreenLeft()` on dispose — dropping the pending load and clearing both the chooser and any purchase failure — but **only when `isChangingConfigurations` is false**, because a rotation disposes too and treating that as leaving would silently swallow the tap; and each view model refuses a plan load while a purchase is in flight, and a second `launchPurchaseFlow` while one is already running, so no chooser opens behind Play's sheet and a double tap on Continue hands off once. The Upgrade affordance is a shared `UpgradeButton` that renders that busy state, since both legs are multi-second waits in which a tap is deliberately discarded — a button that still looked live would be the dead button again. The failure vocabulary from #72 is unchanged and there is deliberately **no third silent path**: a base plan with no purchasable offer is `PRODUCT_UNAVAILABLE`, a dropped service is `BILLING_UNAVAILABLE`, and a plan load that fails is reported on the screen that asked exactly as a refused hand-off is — the chooser never opening is the dead button in a new place.
- **Acknowledging purchases:** `updateSubscriptionStatus` acknowledges every PURCHASED, not-yet-acknowledged purchase. Play **refunds** a subscription that is never acknowledged within three days, so without it a user pays, goes ACTIVE, and silently loses it. Nothing acknowledged before #72, which was harmless only because the Upgrade button never reached Play at all — making the button work is what made this reachable. Each acknowledgement is **bounded** (`ACKNOWLEDGE_TIMEOUT_MS`) and its token leaves the in-flight set in a `finally`: Play's callback is not guaranteed to arrive, and a token stuck in flight is never retried by any later query — which lands back on the same silent refund. The set still dedupes, because the same purchase reaches the client from both `onPurchasesUpdated` and the query that follows it.
- **Resolving entitlement at launch (#72):** `connect()` runs a **ladder** of `RESOLVE_ATTEMPTS` connect-and-query attempts with doubling backoff, guarded by an `AtomicBoolean` so two callers cannot race two ladders, and stops as soon as `_statusResolved` is true (a completed purchase sets it on its own). This is not belt-and-braces: `statusResolved` is what every gate waiting on billing keys off and is only ever set by a query Play answered, so a single launch-time attempt that timed out left it false for the whole session — and `CloudSyncManager.canSyncNow()` then refused a paying subscriber until they restarted the app.
- **Billing client seam:** `PlayBillingRepository` takes a `BillingClientFactory` rather than calling `BillingClient.newBuilder` itself, so the hand-off logic above is unit-testable on the JVM (`PlayBillingRepositoryTest` drives a mocked client through every failure path). Both bindings live in `di/BillingModule`. Those tests need `android.util.Log` **and** `android.text.TextUtils` mocked (`BillingFlowParams.build()` validates through the latter) plus a `Dispatchers.setMain`, or the main-thread launch throws and every success looks like `LAUNCH_FAILED`.
- **Billing seam:** `BillingRepository` is an interface; production binds `PlayBillingRepository` in `di/BillingModule`. Instrumented tests replace *only* that module via `@TestInstallIn(replaces = [BillingModule::class])` with `FakeBillingRepository`, whose `setStatus()` / `setUnresolved()` drive entitlement directly, whose `plans` are what `loadSubscriptionPlans()` answers and whose `lastPurchasedPlan` records which plan the screen actually bought (`nextLoadFails` refuses a plan load, the step before the hand-off) — a real Play connection never resolves on a CI emulator, so every gated flow would otherwise read FREE. `nextLaunchFails` makes one hand-off come back refused, which is how the upgrade-failure path is tested without Play. Same shape as the recorder seam.
- **Subscription gate:** Premium features (Drive sync, extended recording) gated via `SubscriptionGate`. Every entry point that starts cloud sync must pass it — the settings toggle and Connect Drive check it directly in `SettingsViewModel`. The app-launch resume in `BackRecorderApp.resumeCloudSync()` is gated *indirectly* and must stay that way: billing has not answered at that moment, so refusing there would lock out a paying subscriber and persisting OFF would erase their setting. `CloudSyncManager.canSyncNow()` carries the gate instead, waiting on `statusResolved` before it acts on `checkCloudAccess()`, and every tick of the resumed loop passes through it. Any new sync entry point must route through that path or check the gate itself.
- **Drive auth:** `DriveAuthManager` owns the OAuth grant via the Play Services Authorization API (`Identity.getAuthorizationClient`). `GoogleSignIn`/`GoogleAccountCredential` are **not** available — removed in play-services-auth 22 — so don't reach for them. It caches the access token for 45 min, re-authorizes silently, and force-refreshes on 401. `grantGeneration` changes whenever the grant does; anything caching account-scoped Drive state (folder ids) must compare it rather than rely on callers to invalidate.
- **Drive seams:** `DriveAuthManager` reaches Play Services through `DriveAuthorizationClient` and builds its REST client through `DriveServiceFactory`; `di/CloudModule` binds both, and instrumented tests replace just that module via `@TestInstallIn(replaces = [CloudModule::class])` — `FakeDriveAuthorizationClient` (no grant until `grantAccess()`, a new token per call) plus a factory aimed at `FakeDriveServer`, an in-process Drive v3 stand-in. The real Drive client, grant state machine and folder logic all still run. Cleartext to the loopback fake is allowed by a **debug-only** network-security config in `app/src/debug`; the release build is untouched, so only `assembleRelease` proves the reflective client's ProGuard keep rules.
- **Drive folder layout:** `BackRecorder/staging` holds segments; `recovery_<timestamp>` folders are siblings under `BackRecorder/`, never inside `staging`. Anything inside `staging` is deleted once it ages past the 24h buffer, so a recovery folder placed there takes its contents with it.
- **Targeting API 36 (#69):** `compileSdk` and `targetSdk` are both 36, which Play requires, and several platform behaviours follow from that number rather than from anything in the code. Edge-to-edge is **enforced** — `windowOptOutEdgeToEdgeEnforcement` is ignored, so the system bars are always drawn behind the app and only the icon tint (`isAppearanceLightStatusBars`, in `BackRecorderTheme`) is still ours. `Window.setStatusBarColor` is a deprecated no-op **only on API 35+** — below 35 it is still honoured, so `BackRecorderTheme` must not call it: the write would repaint the bar opaque over the transparent one `enableEdgeToEdge()` sets in `MainActivity.onCreate`, and the bar would then look different on API 26-34 than on 35+. Insets are taken in two places: both `Scaffold`s pass `contentWindowInsets = WindowInsets.safeDrawing` rather than the system-bars default, **and** both `TopAppBar`s pass a matching `windowInsets`, because `TopAppBarDefaults.windowInsets` is system-bars-only and the bar would otherwise sit under a landscape display cutout while the body below it cleared one. Back is delivered through `OnBackInvokedCallback` only **on Android 16+ devices** — there `onBackPressed()` is not called and `KEYCODE_BACK` is not dispatched (an older device running this target still dispatches both) — so back navigation works purely because `android:enableOnBackInvokedCallback="true"` lets AndroidX `OnBackPressedDispatcher` (and so Navigation Compose) register; it is declared on `MainActivity` rather than left to a default: `false` is still a documented opt-out at this target, so the attribute is read, and the platform docs do not state what it defaults to at a given `targetSdk` — do not rely on that. And `screenOrientation` / `resizableActivity` / aspect-ratio restrictions are ignored on displays at or above sw600dp, so landscape and activity re-creation are unavoidable there; nothing in the manifest tries to restrict them, and anything that would must instead survive re-creation.
- **Notifications:** Three channels — recording, cloud sync, recovery — all created by `NotificationChannels.createAll()`. Instrumented tests must call it themselves: `HiltTestApplication` replaces `BackRecorderApp`, and a foreground service posting to a channel that doesn't exist kills the process with `CannotPostForegroundServiceNotificationException`.
- **Instrumented tests:** `testInstrumentationRunner` is `com.backrecorderapp.HiltTestRunner`, which swaps in `HiltTestApplication` — the real `BackRecorderApp` connects billing and resumes cloud sync on create, which no test should do. Compose UI tests use `@HiltAndroidTest` + `HiltAndroidRule` + `createAndroidComposeRule<MainActivity>()`; `ComposeHarnessSmokeTest` is the reference. Seed preferences in a rule ordered *between* the cleanup rule and the compose rule, not in `@Before` — the compose rule launches the activity before `@Before` runs, and `NavGraph` fixes its start destination from `disclaimerAccepted` on first composition. CI runs them in the `Instrumented tests` job of `.github/workflows/ci.yml`, on a hosted emulator with a cached AVD; locally they need an emulator or device (`./gradlew :app:connectedDebugAndroidTest`). The `main: PR + green CI` ruleset now **requires** that check alongside `Build and test`, with no bypass actors — so a flaky instrumented test makes every PR unmergeable with no admin override, and test stability here is a production concern for the repository itself.
- **Shared instrumented harness:** `androidTest/.../testing/InstrumentedTestSupport.kt` owns what every flow test repeats — `awaitUntil` and the `RecordingService`/recorder waits built on it, `clearRecordedState(segmentDao)`, `createNotificationChannels()`, `PreferenceSnapshot` (capture a preference before seeding, `restoreAll()` on the way out) and `cleanUpRule(hiltRule) { … }`. **Seeding stays in each test** — that is the part that genuinely differs. Rules go in this relative order (the `order` numbers are whatever makes that come out, since not every test has all of them): the Hilt rule, then `GrantPermissionRule` where a granted start is wanted, then `cleanUpRule`, then the test's own seeding, then the compose rule if there is one — `DriveSyncE2eTest` and `RecordingSegmentTest` drive `ActivityScenario` themselves and have none. Cleanup must sit *outside* seeding, never in the same rule and never in an `@After`: `ExternalResource` skips its own `after()` when its `before()` threw, so a seeding failure would otherwise leave rows, cache files and flipped preferences for the next test in the shared process. `cleanUpRule`'s `before()` is also where `hiltRule.inject()` happens, so seeding below it can use the injected fields. `FakeAudioRecorderFactory` also carries two hooks for driving failure and timing, both reset by `reset()`: `failNextStart()` makes one segment's recorder refuse to open, and `holdStarts()` parks every later recorder inside `start()` until its latch is counted down — which is what turns "teardown landed mid-rotation" from a race a test can only hope to hit into a deterministic one. Release a held latch in a `finally`, or the service never stops and the cleanup rule hangs. Note that a test which stops the service within milliseconds of starting it is killed by the framework with `ForegroundServiceDidNotStartInTimeException` before any assertion runs — let a segment open first.
- **Instrumented test isolation:** `androidTest` runs under the **AndroidX Test Orchestrator** with `clearPackageData=true` (`app/build.gradle.kts`), so every test gets its own process and a `pm clear` of the app and test packages — fresh DataStore, Room database, cache dir, notification channels and **revoked runtime permissions**. Don't turn this off: runtime grants are package-wide and permanent for an instrumentation run, so `RecordingSegmentTest`'s `GrantPermissionRule` would otherwise leak `RECORD_AUDIO` into every later class and make a denied-permission test pass vacuously. Still seed the state a test depends on explicitly rather than relying on the clear. Note a bare `adb shell am instrument` bypasses the orchestrator entirely — use `./gradlew :app:connectedDebugAndroidTest`.
- **Runtime permissions in tests:** two platform behaviours constrain every test here. Revoking a permission in-process SIGKILLs the app's processes, which under instrumentation is the test run itself; and granting `RECORD_AUDIO` through the dialog to an already-running app does the same. So: **`GrantPermissionRule` for granted paths, UI Automator for denied paths** — the dialogs are system UI, outside Compose's semantics tree, and `SystemPermissionDialog` (deny-only, by design) reaches them. A test depending on an un-granted start asserts that precondition. `FirstLaunchFlowTest` covers the granted path, `FirstLaunchPermissionDeniedTest` the declined one (it is what proves both permissions are requested), and `ReturningLaunchFlowTest` the already-accepted launch.
- **`BootReceiver` and Hilt:** `BootReceiver` resolves `AppPreferences` through `EntryPointAccessors`, **not** `@AndroidEntryPoint`. Under instrumentation `HiltTestApplication`'s component is built by `HiltAndroidRule`, so a manifest-registered `@AndroidEntryPoint` receiver that catches `BOOT_COMPLETED` before the first test aborts the whole run. Any new manifest-registered receiver needs the same treatment.
