# Back Recorder

Android background audio recorder with Google Drive sync and in-app billing.

Kotlin 17 · Jetpack Compose/M3 · Hilt (KSP) · Room · DataStore · WorkManager · Play Billing · Google Drive API · Gradle version catalog (`gradle/libs.versions.toml`) · Tests: JUnit 4, MockK, Turbine, Espresso, Compose UI test (instrumented)

Single `:app` module. Package root: `com.backrecorderapp`.

## Key Concepts

- **Segments:** Recordings are composed of segments — recording can be interrupted and resumed.
- **Recording state:** `RecordingService` exposes static `isRunning: StateFlow<Boolean>`. UI observes this directly — no DataStore pref. `AppPreferences.wasRecordingBeforeShutdown` is only for crash-recovery restart.
- **Segment flushing:** `SaveRecordingUseCase` → `RecordingFlusher.flushCurrentSegment()` finalizes the in-progress segment (writes MP4 MOOV atom) for `MediaExtractor`. Flusher is a Hilt interface backed by `RecordingService.flushCurrentSegment()` (static). Rotation guarded by `Mutex`.
- **Service teardown and rotation (#48):** four rules the recording loop depends on, none of them obvious from the code alone. (1) **`onDestroy` never blocks.** It cannot join the rotation — it runs on the main thread, a cancelled rotation cannot abandon a native muxer call part-way, and a join measured in seconds is what the foreground-service timeout and the ANR watchdog count against (observed: a 3 s join produced `ForegroundServiceDidNotStartInTimeException`). Instead `destroyed` and `audioRecorder` are both `@Volatile` and each side writes its own before reading the other's — `onDestroy` sets `destroyed` then reads `audioRecorder`, `startNewSegment` publishes the recorder then re-reads `destroyed` — so at least one of them stops a recorder opened during teardown. Keep that write-then-read order on both sides or the orphan comes back. (2) **The rotation loop catches its own errors**, `CancellationException` rethrown first (it extends `IllegalStateException`, so a bare `catch (e: Exception)` swallows teardown). One IO or database error used to cancel `rotationJob` silently for the rest of the session. The subtle part: `rotateSegment` stops the recorder *before* the waveform write, finalize and prune, so a throw in that stretch must not skip the reopen — it is held in a local and rethrown only after `startNewSegment()`/`startAmplitudeCapture()` have run. Skipping the reopen leaves the service alive, holding the wake lock and the notification, capturing **nothing** until the next tick; rethrowing matters too, or a flush whose finalize failed reports success and `SaveRecordingUseCase` proceeds on a segment that was never completed. `amplitudeBuffer` is drained and cleared by each rotation, capped as a backstop, and every access goes through `withAmplitudeBuffer` — `onDestroy` cannot join the amplitude coroutine, so a lock is the only thing covering that path. (3) **A recorder that will not start is fatal**, not logged: `startNewSegment` discards the row and file it reserved and throws `SegmentStartException`, and the loop and the flush collector stop the service rather than write an empty segment a minute behind a notification claiming to record. The stop waits `FOREGROUND_SETTLE_MS` first — leaving the foreground within milliseconds of entering it gets the process killed — and uses `stopSelf(startId)` so a recording the user begins during that settle is not torn down. It also abandons outstanding flushes, clears `wasRecordingBeforeShutdown` (so crash recovery does not restart a session that just failed the same way) and posts a notification on the recovery channel: a service that disappears silently leaves someone who started a background recording hours ago to find out from an empty save. (4) **`amplitudeJob` is cancelled *and joined*** before `rotateSegment` reads the buffer; cancellation alone is a request, and the old comment calling it safe was wrong.
- **Starting and stopping (#61, #62):** `onStartCommand` is idempotent. `startForeground` runs on *every* start, redelivered `START_STICKY` intents included — a start that returns without reaching the foreground is killed with `ForegroundServiceDidNotStartInTimeException` — and the `recordingStarted` guard sits immediately after it, so a double tap or `BootReceiver` racing an app start no longer opens a second recorder over the live one (orphaning the first, microphone and all) or overwrites `rotationJob`/`flushJob` with a second set. `stopBecauseRecordingFailed` clears that guard, because `stopSelf(startId)` is a no-op once a newer start has landed and a service left with the guard set would stay alive, in the foreground, recording nothing, with the UI's toggle unable to recover it. Stopping also **closes the segment that was open**: `closeOpenSegment()` hands the work to an injected `@ApplicationScope` scope (`onDestroy` cannot block and `serviceScope` is cancelled on the way out) and `closeCurrentSegment()` claims it under `rotationMutex`, so it is closed exactly once and never interleaves with a rotation. A segment with bytes on disk is finalized; one with a zero-length file is `discardSegment`ed, because a finalized row is a claim that `filePath` holds readable audio and `getSegmentsInRange` would hand that claim to every save. Every write of `currentSegment` is under that same mutex for the same reason — including the first one, in `startRecordingLoop`. Leaving the segment open was one orphan row plus its `.m4a` and `.bin` per session, permanently: `pruneOldSegments` only deletes complete rows, and `getSegmentsInRange` matches `isComplete = 0` forever.
- **Flush handshake:** the request/serve handshake lives in `FlushCoordinator` (`service/`), a static field of `RecordingService`'s companion. Requests go through an **unlimited `Channel`**, never a `SharedFlow` — a channel buffers with no receiver, so a flush asked for in the window between `_isRunning` flipping true and `flushJob` starting is queued rather than dropped. `onDestroy` calls `abandonAll(FlushAbandonedException())` *before* cancelling the jobs, so queued and in-flight requests fail instead of hanging. Because the coordinator is process-global it also enforces the inverse. It carries an `Epoch` (id + accepting): `abandonAll` bumps it and stops accepting, `reopen` — called from `onStartCommand`, **not** from the collector, or window 1 would reject requests for every session after the first — bumps it and accepts again, and `requestFlush` compares the epoch after enqueueing, so a request racing teardown (or teardown *and* restart, which a plain boolean would flip back) fails fast instead of being stranded for the next service instance. A caller that gives up cancels its own deferred so the collector skips it rather than rotating a later recording for a save that already failed. `SaveRecordingUseCase` additionally wraps the call in `withTimeout(FLUSH_TIMEOUT_MS)` and maps a timeout to `SaveResult.Error`, which `MainViewModel` surfaces as a retryable error and which deletes the empty SAF file. Three layers, all deliberate (#47): never drop, never abandon, never wait forever.
- **The save runs off the main thread (#93):** `SaveRecordingUseCase.execute` is a one-line `withContext(@IoDispatcher)` around `performSave`, which holds what used to be `execute`'s body. Its only production caller is `SaveCoordinator.runSave` on the `@ApplicationScope` (an instrumented test calls it directly too); before #111 it was `MainViewModel.saveRecording` on `Dispatchers.Main.immediate`, and trimming, `concatenateM4aFiles` (a `MediaMuxer`/`MediaExtractor` loop over every segment) and the `copyToUri` stream copy are seconds of blocking work on a multi-segment save — an ANR, with the `saveInProgress` spinner unable to render while it ran. The split into two functions is not cosmetic: `withContext` takes a lambda, so the early returns that the gate, the empty-segment checks and the flush failure all depend on would each have become a `return@withContext`. The view model's `_uiState` writes stay on main, which is what the read-modify-write safety documented under #74 rests on: since #111 it never calls `execute` at all, and only collects `SaveCoordinator`'s `saving` and `outcomes` flows on `Dispatchers.Main.immediate`. The use case's dispatcher is injected rather than `Dispatchers.IO`, and the **test** is the reason that matters twice over: it asserts by *thread name* that the trim and the SAF write ran off the caller's thread (handing it the dispatcher proves nothing about where the blocking work went), and the flush-timeout test now has its `delay` intercepted by that dispatcher instead of by the one `runTest` installs — so `SaveRecordingUseCaseTest` shares one `TestCoroutineScheduler` between the two by setting it as `Dispatchers.Main`, which bare `runTest` adopts. Drop that sharing and the ten-second `FLUSH_TIMEOUT_MS` leaves virtual time and the test waits it out for real. The move also made the Save affordance live again the moment the body suspends, so a **second save could start while the first ran** — two of them each force a `flushCurrentSegment` rotation of the live recording and race over the `cacheDir` temp files — and it made the save outlive the view model that started it. Both are handled by `SaveCoordinator` — the next bullet.
- **The save's claim and lifetime are process-scoped (#111):** `SaveCoordinator` (`domain/`, `@Singleton`) owns the one save slot, runs the save on the `@ApplicationScope`, and carries its outcome; `MainViewModel` only observes it (`saving` → `saveInProgress`, `outcomes` → the snackbar/upgrade dialog). It used to be a `saveInProgress` flag in the view model guarding a save launched under `NonCancellable` in `viewModelScope`: back out mid-save, relaunch, and the fresh instance read `false`, so both guards passed and a second save ran alongside the first; and a failure after the user left was written into a state nothing collected. This is the conclusion #78 reaches for billing — in-flight state of work that outlives a screen has to live somewhere the screen does not. Four things about the shape. (1) **The claim is taken in `requestSave`, synchronously, before anything suspends**, and held across the SAF picker as a `SaveClaim` token. Not when the picker answers: the picker creates its 0-byte file the instant it returns a URI, so a refusal after that point is the empty recording #23 exists to prevent, and a claim taken there let a double tap put two coroutines past the guard and open two `CreateDocument` pickers. Every path that does not reach the picker (empty range, gate refusal, a throw) gives the claim back in a `finally`; the picker's cancel (`onSavePickerCancelled`) and `onCleared` give back a claim whose picker never answered — a leaked claim is Save dead for the life of the **process** now, not just the view model. `release` ignores a claim whose save has started, so neither can free a running save's slot. A picker result arriving with no claim (a fresh view model after a process death) asks for one — and saves the fresh state's range, not the one the user picked, since the selection is not restored ([#135](https://github.com/jacoelt/backrecorder/issues/135)); a refusal deletes that result's file via `discardPickerResult`, which never deletes the URI the running save is writing — both pickers suggest the same name, and a provider that overwrites hands back the same document. (2) **The application scope replaced `NonCancellable`**: it is never cancelled, so the save and its cleanup (`deleteOutputUri` on any non-success, a binder call kept on the IO dispatcher) always finish together, and the slot is freed in an unconditional `finally`. That scope has a `SupervisorJob` and no handler, so `runSave` catches everything — `getSegmentsInRange` and `checkSaveAccess` sit outside `performSave`'s own `try`, and an escaping throw would kill the process. (3) **Outcomes go through an unlimited `Channel`**, for the `FlushCoordinator` reason: it buffers with no receiver, so an outcome reached while no screen is open is shown by the next one. When no collector is attached (counted by `onStart`/`onCompletion`; `MainScreen` collects through `collectSaveOutcomes()` under `repeatOnLifecycle(STARTED)`, **not** from `viewModelScope`, because the view model survives Home and sits under Settings where no snackbar can be seen — collecting for its life made the commonest ways of leaving mid-save the silent ones), a failure is **also** posted through the `SaveFailureNotifier` seam on the recovery channel — the audio is still only in the 24h buffer and the user has to save again — generic text only, since an exception message may carry a URI. Only `Failed` is notified — never success, and never `UpgradeRequired`, which is an entitlement refusal rather than a failure and would be misdescribed by "try again". Like the #84 upload notification it drops silently when POST_NOTIFICATIONS was never granted, so the queued in-app message is then the only report. (4) **What is not covered: a process kill mid-save.** Nothing holds the process up once the screen is gone (the recording service only while recording), so a kill during `concatenateM4aFiles`/`copyToUri` still leaves a partially written SAF file plus orphaned cache temps; closing it needs a foreground-capable worker and is [#128](https://github.com/jacoelt/backrecorder/issues/128). The same root cause bites without a kill: with no foreground service the process is cached after Home and may be **frozen** (Android 14+), so the save — and the notification (3) describes — can stall until the app is reopened.
- **Recorder seam:** `RecordingService` records through `AudioRecorderFactory` / `AudioRecorder` (`service/recorder/`), not `MediaRecorder` directly. Production binds `MediaRecorderAudioRecorderFactory` in `di/RecorderModule` — same MPEG-4/AAC 16 kHz mono 32 kbps configuration as before. Instrumented tests replace *only* that module via `@TestInstallIn(replaces = [RecorderModule::class])` with `FakeAudioRecorderFactory`, whose `FakeAudioRecorder` encodes a synthetic tone through `MediaCodec` + `MediaMuxer`, so segments are real MP4s with a MOOV atom that `MediaExtractor` reads. A recorder instance is single-use: one `start()`, one `stop()`, one per segment. Inside `MediaRecorderAudioRecorder`, `PlatformRecorder` holds every `MediaRecorder` call and no decisions, so the release ordering (#48) is unit-testable on the JVM, where `MediaRecorder` cannot be constructed. The recorder field is guarded by one monitor taken by `start()`, `stop()` **and** `maxAmplitude()` — neither `@Volatile` nor an `AtomicReference` is enough, because `onDestroy` and a rotation can both reach `stop()` (a read-then-clear lets both release the same native recorder) and because an amplitude read that loads the reference and then calls through it in two steps can have the release land in between. The cost is that an amplitude read blocks for the length of one `MediaRecorder.stop()`, once per segment, which is the right trade against a native use-after-release. `stop()` may throw and releases regardless; `maxAmplitude()` reads 0 from the moment teardown begins. `FakeAudioRecorder` honours that contract too, but answers from a `@Volatile` flag rather than its encode lock — holding that lock would park the service's amplitude coroutine for a whole `feed()` and starve `Dispatchers.Default`, which is two threads wide on a CI emulator.
- **Minute-snapped selection:** Waveform *drag handles* snap to minute boundaries (start floors, end ceils). End handle clamps to `bufferEndTime` so the currently-recording minute stays reachable. Time-preset chips do **not** snap — they select an exact duration from the recording edge (#21).
- **WaveformView touch:** Custom `awaitEachGesture` pointer-input loop (not `detectHorizontalDragGestures`). Dedicated handle zones above/below waveform; 2D distance disambiguates overlapping handles.
- **Billing:** `BillingRepository` reports subscription status (FREE/ACTIVE); the money is taken by Play, not in-app. The app's only write is `launchPurchaseFlow`, which puts the user in front of Play's purchase sheet.
- **The upgrade hand-off (#72):** `launchPurchaseFlow` is **suspend and answers its caller** — null when the sheet was shown, a `PurchaseFailure` when it was not — rather than publishing on a shared flow. That shape is the fix, not an accident: both `MainViewModel` and `SettingsViewModel` offer the upgrade, and `MainViewModel` stays alive in the nav back stack while settings is on top, so a broadcast refusal in settings also latched an error on the main screen that fired whenever the user next went back. A per-call answer reaches only the screen that asked. The failure is the *user-visible* half; the response code and debug message go to logcat under the `PlayBilling` tag. Six things keep a hand-off from going quiet, which is the whole defect the issue reported. (1) A `Mutex` **serializes** hand-offs rather than dropping them — two overlapping attempts would open two connections on the one client, which Play answers with an error, but a *dropped* second tap is just as bad, because the second caller is usually the other screen and would be left with nothing to show (#78 bounds the wait for it — see that bullet). (2) One shared `CompletableDeferred` per connection attempt, so a purchase started while the app-launch `connect()` is still connecting waits for that attempt instead of issuing a second `startConnection` — otherwise an Upgrade tap in the first seconds after launch reports "unavailable" over a connection that succeeds a moment later (who may *complete* that deferred is #78's bullet). (3) `withTimeoutOrNull` bounds **only** connecting and querying — the lock wait got its own, separate bound in #78 — and the block it wraps returns a non-null `Prepared`: wrapping the launch too would cancel after Play had already shown the sheet, and returning a bare nullable made "timed out" and "the sheet opened" the same value — that conflation shipped a version where *every successful purchase* reported a failure, which is what the unit tests now pin. (4) `onBillingServiceDisconnected` answers the pending request, since the service can die while setup is still pending and the setup callback then never arrives. (5) Everything is wrapped in a `try`/`catch` returning `LAUNCH_FAILED` (rethrowing `CancellationException`), because a throw out of the Play client would otherwise reach `viewModelScope` and take the app down. (6) A `SERVICE_DISCONNECTED`/`SERVICE_UNAVAILABLE` product query **reconnects and asks once more** (`OfferQuery.Failed.retryable`), because the binding can drop between the `isReady` check and the query — the client reports ready right up to the moment it dies, so no check closes that window; `ITEM_UNAVAILABLE` is deliberately *not* retryable, since Play not having the product is not transient. `launchBillingFlow` itself must run on the main thread — off it Play returns `DEVELOPER_ERROR` and shows nothing — and the activity is re-checked for `isFinishing`/`isDestroyed` first, because preparing crosses a callback and the screen may be gone by then. From the product query, only `ITEM_UNAVAILABLE` or an OK-but-empty product list means `PRODUCT_UNAVAILABLE` (#74 adds one more source of it: a chosen base plan that carries no purchasable offer) (a Play Console problem: no such product, no active offer on the base plan, an account not on a buying track); every other response code is `BILLING_UNAVAILABLE`, because telling a tester their product is misconfigured when the network dropped sends them to fix the wrong thing.
- **Choosing the plan (#74):** the subscription is `main_subscription` — not `premium`, which is what the app asked Play for until #74 and which does not exist, so every Upgrade tap came back `ITEM_UNAVAILABLE`. **No test can catch a drift in that string**: every test fakes billing, and the only authority on it is the Play Console. It carries two base plans, `monthly` and `yearly`, each with a free-trial offer, which is why correcting the id alone would have been worse than leaving it broken — the hand-off took `subscriptionOfferDetails.firstOrNull()`, an ordering Play does not contract, so one tap would have charged an **arbitrary** plan, possibly a year the user never chose. So `loadSubscriptionPlans()` is a separate call from `launchPurchaseFlow(activity, plan)`, and the plan is required rather than defaulted: there is no fallback that is not an arbitrary charge. Offers are matched by `basePlanId` (via `BillingPeriod`, which owns those two strings) and **never by position**; within a base plan the trial offer wins, and no eligibility check is needed because `queryProductDetailsAsync` already returns only the offers this account can take. Prices are Play's own `formattedPrice` from `pricingPhases` — the recurring phase, not the free one in front of it — and are never assembled by hand, because a locale's separator, symbol and symbol position are not ours to guess; `priceAmountMicros` exists for arithmetic only. The yearly saving is **computed** (yearly vs monthly × 12) rather than written into the app: the ratio is a Play Console decision that can change without a release, so a hard-coded "17%" would become a lie in the UI, and the badge is hidden outright when the figure would mislead — one plan only, two currencies, or a yearly price that is not actually cheaper. The purchase re-resolves the offer from a fresh query rather than carrying the chooser's token, because the token and the `ProductDetails` handed to `launchBillingFlow` must come from the same response and the chooser's may be minutes old — so what crosses that gap is the *identity* of what the user picked (base plan **and** `offerId`, since a base plan may carry several eligible offers and "whichever came first" is the same ordering this change refuses to trust), with the preference rule only as a fallback and a vanished base plan failing closed. `loadSubscriptionPlans()` takes the same `purchaseMutex` and `PREPARE_TIMEOUT_MS` and maps a timeout or a throw to `BILLING_UNAVAILABLE`; it wrapped the **lock** inside that same budget until #78 split the two — see that bullet. The chooser's selection is `rememberSaveable`: orientation cannot be restricted at this target on large screens, and a rotation that silently reverted the selection to the default would buy a year the user did not pick. Keeping the chooser from latching is the #72 defect in a new place, and the guard is a **generation counter, not cancellation** — two of them, `planLoadGeneration` and `purchaseGeneration`. Dismissing the offer bumps only the load's, because a purchase already on its way to Play is not what that dialog started; leaving the screen bumps both. An answer carrying a stale value is dropped rather than written. A generation decides only whether an answer is **published**; it never frees a busy flag, because the call is still running and that flag is the only thing stopping a second one. So abandoning leaves `plansLoading` / `purchaseInFlight` set and each `finally` clears its own unconditionally — which also means two operations of a kind can never overlap **within one view model**. Across the two it is the repository's mutex that serializes them, not the flags, so a hand-off begun on the main screen and one begun in settings queue on that mutex — and since #78 a waiter that is still queued after `LOCK_WAIT_TIMEOUT_MS` is refused with `BILLING_BUSY` rather than waiting indefinitely ([#118](https://github.com/jacoelt/backrecorder/issues/118) carries the rest of the fix: the in-flight state has to live in the repository). An abandoned load is deliberately **not** re-adoptable, and needs no mechanism to be: every Upgrade affordance renders `plansLoading` and is disabled while it is set, so there is no tap to re-adopt it with — the user sees a spinning, disabled button until it returns, then a live one whose next tap starts a fresh load. A version of this shipped briefly as a `liveLoadGeneration` field that let a tap adopt the running load; it was sound but unreachable, and it made the generation counter non-monotonic — the one property the discard logic rests on — so it came out again. `onScreenLeft` also drops the **upgrade offer**, not just the chooser: it is raised by an action the user never answered, and leaving it set meant it was waiting on screen when they navigated back, which is the same dialog-with-no-tap-behind-it defect. The flags are also the reason nothing may read the whole `MainUiState`, suspend and write `state.copy(…)` back: that restores a flag the owning `finally` has already cleared, and since nothing else clears it the Upgrade button stays a disabled spinner for the life of the view model — `requestSave` did this, and every write in it now goes through the current value. Clearing them on the way out was a real defect in both directions: the user could leave a hand-off running, come back or cross to the other screen, pick the other plan and be shown **two** Play sheets, the first for the plan they had moved on from — the arbitrary charge this issue exists to prevent, reached through the UI instead of through `firstOrNull()` — and a freed load guard let the next tap queue inside `purchaseMutex` behind a load nobody was waiting for, spending its whole timeout on the lock and reporting `BILLING_UNAVAILABLE` over a working connection (since #78 that queue is bounded and reports `BILLING_BUSY`, but the guard is still what stops the tap). The counters are plain `Int`s because every mutator runs on the main thread (a Compose lambda, or a `viewModelScope` body on `Dispatchers.Main.immediate`), which is equally what makes the `_uiState.value = _uiState.value.copy(…)` read-modify-writes safe; calling one from another dispatcher would break both at once. One counter for both was wrong in a way worth remembering: Cancel on an offer dialog re-raised during a hand-off threw away that live purchase's answer and freed the guard that stops a second one. Cancelling the coroutine instead would be worse again, and this is the subtle part: it is suspended inside `PlayBillingRepository`, whose connection attempt is **shared by every caller**, and a cancelled caller's `finally` used to complete that shared deferred with a failure — answering the launch-time resolve ladder, which is what `statusResolved` and so cloud sync for a paying subscriber depend on, with a refusal nobody asked for. #78 removed that half of it; the reason not to cancel stands anyway, since a cancelled caller still abandons an attempt the ladder may be waiting on. (View-model teardown still cancels it, but nothing is watching by then.) **Both** view models need this: `MainViewModel` outlives its screen (settings sits on top of it), and `SettingsViewModel` does too, because settings navigates *forward* to the disclaimer and keeps its back-stack entry. Each screen calls `onScreenLeft()` from `onDispose`, but **only when `isChangingConfigurations` is false** — a rotation disposes too, and treating that as leaving would silently swallow the tap. Each view model also refuses a plan load while a purchase is in flight, and a second `launchPurchaseFlow` while one is already running, so no chooser opens behind Play's sheet and a double tap on Continue hands off once. `MainUiState.purchaseInFlight` and `SettingsViewModel.upgradeBusy` exist to *render* that — a tap is being discarded, so the button must not look live. `upgradeBusy` is `SharingStarted.Eagerly`: under `WhileSubscribed` its `value` answers from a stale cache whenever nothing is collecting. Both affordances are a shared `BusyButton` — `UpgradeButton` and the chooser's Continue — since both legs are multi-second waits in which a tap is deliberately discarded, and a button that still looked live would be the dead button again. The chooser **stays up, with Continue busy**, until Play has the sheet: closing it on Continue left the main screen with no dialog, no spinner and nothing disabled for the length of the hand-off, because `MainScreen` renders `purchaseInFlight` only inside the upgrade dialog — which the plan load had already closed. Settings never had that gap (its card button is always on screen), and a shared component is no use if only one screen is in a position to render the state. The failure vocabulary from #72 gained only `BILLING_BUSY` in #78, and there is deliberately **no silent path**: a base plan with no purchasable offer is `PRODUCT_UNAVAILABLE`, a dropped service is `BILLING_UNAVAILABLE`, and a plan load that fails is reported on the screen that asked exactly as a refused hand-off is — the chooser never opening is the dead button in a new place.
- **Who owns the Play connection (#78):** `purchaseMutex` and the shared connection deferred were owned by whichever caller happened to be first, and callers come from two screens plus the launch ladder. Two consequences, one root cause. (1) **An attempt belongs to no caller: only Play's own callback completes it.** `ensureConnected`'s `finally` used to complete the shared deferred with `BILLING_UNAVAILABLE` whenever *its own* caller gave up — a timeout, or a cancelled `viewModelScope` — so an abandoning caller handed every other waiter a refusal none of them caused while the real `startConnection` was still outstanding and still owned Play's only callback. The waiter that matters is the resolve ladder in `connect()`: `statusResolved` is what every billing gate keys off, so one Upgrade tap backing out could leave a paying subscriber refused cloud sync for the whole session. Abandoning now only takes the attempt **out of the slot** — that part is still required, or every later caller would join a deferred nothing will ever complete and no reconnect would be tried — and anyone still awaiting it is bounded by their own budget and gets the real answer if Play does come back. The two halves are not symmetric and both are load-bearing: *don't complete* is the fix, *do unpublish* is what keeps it from stranding. One exception, and only one: a `startConnection` that **throws** registered no callback, so nothing can ever answer that attempt — it is completed on the spot, because leaving it would make an already-joined ladder wait out its whole budget for a connection that was never attempted. Two residuals are deliberate rather than overlooked. A later caller arriving after an abandonment still issues a **second `startConnection`** over one Play may not have finished; the client answers the new listener non-OK synchronously and leaves the first listener owning the eventual callback, so that caller fails fast rather than joining — unchanged from before #78, and the alternative (keeping an unanswerable attempt published) is the stranding above. And a connection that succeeds *after* every waiter has gone used to resolve nothing: `connect()` runs its ladder once per process, and on a cold start where Play binds slowly every rung after the first is refused synchronously (the client is still connecting), so the ladder exhausts in about a minute and the first attempt's late success left `statusResolved` false for the session. The same end state is reachable without a late callback: a ladder whose rungs were all refused quickly is over before Play is back, and a later plan load connects fine but only asks for offers. Since [#119](https://github.com/jacoelt/backrecorder/issues/119) every **OK** `onBillingSetupFinished` calls `resolveEntitlementIfUnresolved`, which runs one bounded entitlement query on the `@ApplicationScope` when `statusResolved` is still false and no ladder is running (a running ladder queries after its own connect). That skip is a promise that a later rung will query, which the **last** rung cannot keep — an OK racing its timeout, or landing on the main thread before `resolving` clears — so `connect()`'s `finally` re-checks once the flag is down and queries if the client is ready and entitlement is still unresolved. It hangs off Play's callback rather than a watcher of the abandoned attempt — that was the first version and is wrong: it had to be bounded per abandonment, missed a success landing between a caller's timeout and its unpublish, and never saw the fresh-connection case at all. Having a ladder rung re-check `isReady` was rejected too, since it only helps while the ladder is still running. A late query that does not resolve logs at `Log.w` and is not retried — the next successful connection asks again — and the body is wrapped because that scope has no handler. Because an abandoned attempt is now left uncompleted, the connection callbacks log through `connectionFailed` rather than `reportFailure`: the first ordinary Play restart afterwards lands in `onBillingServiceDisconnected`, and `reportFailure` would write "Upgrade hand-off failed" for a hand-off nobody made, into the `Log.w` that `-assumenosideeffects` leaves as release's only evidence (#107). A connection is not a hand-off, so it says so and nothing is suppressed. Gating the log on whether the attempt was still **published** was tried and is wrong: an attempt is unpublished *while still awaited* in precisely the #78 case, so a genuine refusal of those waiters went unlogged — a worse failure than the phantom, and one that recreates #107 in a new place. (2) **The lock wait is timed apart from the Play round trip**, as `LOCK_WAIT_TIMEOUT_MS` and its own outcome `PurchaseFailure.BILLING_BUSY`. The load used to run `withTimeoutOrNull(PREPARE_TIMEOUT_MS) { purchaseMutex.withLock { … } }`, so a load queued behind the other screen's hand-off could burn the whole budget waiting and report "billing unavailable" over a Play it never asked anything — the wrong word for "busy", and it sends a tester to the wrong fix. The hand-off had the opposite shape and waited on the lock with no bound at all; it is bounded the same way now, which is safe for the reason #72's rule turns on — the bound expires strictly **before** anything of Play's is on screen, and `withTimeoutOrNull` still must never wrap `launchBillingFlow`. `LOCK_WAIT_TIMEOUT_MS` is deliberately **shorter** than `PREPARE_TIMEOUT_MS`: a hand-off holds the client for at most one prepare, so an equal bound would make `BILLING_BUSY` a dead heat that never fires, and a waiter stuck behind a Play that is not answering gains nothing by waiting out the full prepare only to be refused anyway. Acquiring the lock inside the timeout and releasing it outside is the documented way to **leak** one — the timeout may land "right before the return from inside of the timeout block", so a `lock()` that already returned can still surface as expired — and because the repository is a `@Singleton` that leak would be permanent: every later hand-off and plan load on both screens reporting busy for the life of the process, which is the dead Upgrade button again. So `acquirePurchaseLock` decides on a `held` flag written only after `lock()` returns, never on `withTimeoutOrNull`'s value, and releases in a `catch` if the caller's own cancellation lands after the acquire (cancellation *while* `lock()` is suspended needs nothing — the mutex releases itself). The pair also raises the worst case a user can see from 20s to **30s**, accepted deliberately: re-sharing one budget is the defect this issue reports. `BILLING_BUSY` reaches both screens without a view-model change because each renders `purchaseError` through `PurchaseFailure.messageRes()`, whose `when` is exhaustive — which is also what makes a new outcome impossible to add silently; its wording names *billing* rather than *a purchase*, since the holder is as often a plan load. **Still open from this issue's comments:** the per-view-model `purchaseInFlight` flags, which guarantee "no second hand-off" only *within* a view model, and the `Activity` captured at Continue rather than a provider, so a rotation mid-hand-off answers `LAUNCH_FAILED`. Both need view-model changes and are [#118](https://github.com/jacoelt/backrecorder/issues/118).
- **Acknowledging purchases:** `updateSubscriptionStatus` acknowledges every PURCHASED, not-yet-acknowledged purchase. Play **refunds** a subscription that is never acknowledged within three days, so without it a user pays, goes ACTIVE, and silently loses it. Nothing acknowledged before #72, which was harmless only because the Upgrade button never reached Play at all — making the button work is what made this reachable. Each acknowledgement is **bounded** (`ACKNOWLEDGE_TIMEOUT_MS`) and its token leaves the in-flight set in a `finally`: Play's callback is not guaranteed to arrive, and a token stuck in flight is never retried by any later query — which lands back on the same silent refund. The set still dedupes, because the same purchase reaches the client from both `onPurchasesUpdated` and the query that follows it.
- **Resolving entitlement at launch (#72):** `connect()` runs a **ladder** of `RESOLVE_ATTEMPTS` connect-and-query attempts with doubling backoff, guarded by an `AtomicBoolean` so two callers cannot race two ladders, and stops as soon as `_statusResolved` is true (a completed purchase sets it on its own). This is not belt-and-braces: `statusResolved` is what every gate waiting on billing keys off and is only ever set by a query Play answered, so a single launch-time attempt that timed out left it false for the whole session — and `CloudSyncManager.canSyncNow()` then refused a paying subscriber until they restarted the app.
- **Billing client seam:** `PlayBillingRepository` takes a `BillingClientFactory` rather than calling `BillingClient.newBuilder` itself, so the hand-off logic above is unit-testable on the JVM (`PlayBillingRepositoryTest` drives a mocked client through every failure path). Both bindings live in `di/BillingModule`. Those tests need `android.util.Log` **and** `android.text.TextUtils` mocked (`BillingFlowParams.build()` validates through the latter) plus a `Dispatchers.setMain`, or the main-thread launch throws and every success looks like `LAUNCH_FAILED`.
- **Billing seam:** `BillingRepository` is an interface; production binds `PlayBillingRepository` in `di/BillingModule`. Instrumented tests replace *only* that module via `@TestInstallIn(replaces = [BillingModule::class])` with `FakeBillingRepository`, whose `setStatus()` / `setUnresolved()` drive entitlement directly, whose `plans` are what `loadSubscriptionPlans()` answers and whose `lastPurchasedPlan` records which plan the screen actually bought (`nextLoadFails` refuses a plan load, the step before the hand-off) — a real Play connection never resolves on a CI emulator, so every gated flow would otherwise read FREE. `nextLaunchFails` makes one hand-off come back refused, which is how the upgrade-failure path is tested without Play. Same shape as the recorder seam.
- **Subscription gate:** Premium features (Drive sync, extended recording) gated via `SubscriptionGate`. Every entry point that starts cloud sync must pass it — the settings toggle and Connect Drive check it directly in `SettingsViewModel`. The app-launch resume in `BackRecorderApp.resumeCloudSync()` is gated *indirectly* and must stay that way: billing has not answered at that moment, so refusing there would lock out a paying subscriber and persisting OFF would erase their setting. `CloudSyncManager.canSyncNow()` carries the gate instead, waiting on `statusResolved` before it acts on `checkCloudAccess()`, and every tick of the resumed loop passes through it. Any new sync entry point must route through that path or check the gate itself — the saved-recording upload (#84) is the second one, and checks `checkCloudAccess()` itself after waiting on `statusResolved`.
- **Complimentary access (#98):** the digest of a redeemed code, held in `ComplimentaryAccessStore` (its own DataStore file), unlocked once by a redeem code typed in Settings, grants premium permanently without Play. It is **entitlement, never a billing status**: faking `SubscriptionStatus.ACTIVE` would send `updateSubscriptionStatus` hunting for a purchase token to acknowledge that does not exist and put these users on the same acknowledge-or-be-refunded path as real subscribers, so the two terms stay apart and are OR-ed. The OR lives in *one* place — the pure `SubscriptionGate.isPremium(status, complimentary)` — and `complimentary` is a **required** parameter rather than a defaulted one, so adding it could not leave `SettingsScreen` or `SettingsViewModel` silently reading billing alone; that silent second copy is the drift #85 exists to prevent, and a default argument is how it would have come back. `statusResolved` becomes `complimentary || billingResolved`, which *narrows* the #87 window for these users rather than widening it: the grant is local and instant, so a Play that never answers no longer leaves them unresolved for the session. It is a `stateIn` on the `@ApplicationScope` now, not a `get()` delegating to billing. The store keeps both a `StateFlow` (for rendering and that OR, seeded `false`) and a suspending `isGranted()` that awaits DataStore — a decision taken in the window before the first read must not take the seed for an answer. Codes are validated **offline** against salted SHA-256 digests compiled into `ComplimentaryCodeValidator`; **no plaintext code is ever in this repository**, which is also why the validator is bound in its own `di/ComplimentaryModule` — instrumented tests replace just that binding with a digest of a code they know, instead of a real one being written down in a test. What the store persists is the **digest of the code that was redeemed, not a bare flag**, and every read re-validates it: with a boolean, `BLOCKED_CODE_DIGESTS` could only refuse the *next* redemption, so in the one scenario the per-person split exists for — a code gets passed around and several installs redeem it — every one of those installs would keep premium forever and the release retiring the digest would change nothing for them. Retiring means adding the digest to the blocked set, never editing the accepted set, so the issued digest stays on record. The code alphabet and length are not cosmetic (`MIN_CODE_LENGTH`, enforced in `accepts`): the digests ship inside the APK, and while patching the gate needs a rebuild, a *cracked* code can simply be typed in by anyone it reaches — so a short code would be a different and worse threat than the one this issue accepts. `normalize` uppercases with `Locale.ROOT` because a Turkish default locale would send `i` to `İ` and the digest with it. The DataStore flow **retries, then degrades to not-granted**, and the order matters: it is collected eagerly on the `@ApplicationScope`, which carries a `SupervisorJob` but no exception handler — an uncaught throw there kills the process on every launch — and it is awaited by `isPremium()`, which sits on the save path *outside* `SaveRecordingUseCase.execute`'s error funnel, so without a guard a corrupt preferences file would crash the save and leave the empty SAF file behind. Entitlement must stay non-throwing. But a bare `catch` is **terminal**: it would end the shared collection, freezing `granted` at false for the life of the process — across a later successful redeem — while `isGranted()`, which collects afresh, went on answering true, so the gate would grant saves while the settings card still read "Free plan". Hence `retryWhen` first, with the `catch` only as the floor under a persistent failure. The store is given its `DataStore` by `di/ComplimentaryDataStoreModule` rather than reaching for a `Context` delegate, which is what makes all of the above reachable from a JVM test on a temporary file; that module is deliberately **separate** from `ComplimentaryModule`, since instrumented tests replace the validator and must keep the real store. The redeem path carries the #74 generation guard — an `ACCEPTED` published after the user left is the render condition for the confirmation dialog, which would then be waiting on screen the next time Settings opened — and its button is a `BusyButton`, because the in-flight guard discards a second tap. A failed *write* is `STORAGE_FAILED`, not `REJECTED`: telling someone holding a valid code that it was not recognised sends them re-typing something that will never work. Nothing hides the upgrade affordances by hand: the main screen's offer is only ever raised by a `GateResult.Blocked`, so the gate's OR removes it, and Settings swaps the plan line for "Complimentary access" because the billing status underneath stays FREE for these users for the life of the install.
- **Connecting Drive turns uploads on (#80):** `connectDrive()` and `onConsentResult()` both finish through `SettingsViewModel.startSyncEnablingUploads()`, which promotes a `cloudUploadMode` of `OFF` to `WIFI_ONLY` and *then* starts the loop. Connecting is the request to upload, so `OFF` at that point is the default nobody chose, not a decision. Leaving it was the whole of #80: consent completed, the settings screen read "Connected", and `canSyncNow()` refused at its **first** gate (`mode == OFF`) for the life of the install — for a paying subscriber, since the premium gate was never what blocked it. The failure was invisible from the UI *and* from a log. Since #107 `canSyncNow()` logs the gate that refuses at `Log.w`, on each loop's first evaluation and then only when the reason changes, so a loop refusing for weeks costs one line rather than none or one per tick. `Log.w` matters: `-assumenosideeffects` in `proguard-rules.pro` strips every `Log.v`/`d`/`i` from release, so only `Log.w`/`Log.e` survive — worth knowing before trusting any absence of logs as evidence. `WIFI_ONLY` rather than `ALWAYS_ON` because opting someone onto cellular data is not ours to assume, and a mode the user already chose is never overwritten. The ungated `restoreSession()` in `init` deliberately does **not** route through this: a grant that outlives a subscription must not resurrect uploads the user switched off. What the Drive row says once entitlement lapses was a separate defect, fixed in #85 — the bullet below. Since #84, `cloudUploadMode` also gates the saved-recording upload (`SavedRecordingUploader`, which returns `DECLINED` on `OFF`), so this one promotion turns **both** kinds of upload on from a single Connect tap.
- **The grant outlives the subscription (#85):** the Drive OAuth grant is **deliberately not revoked** when entitlement ends — re-subscribing should not cost the user a fresh consent round, and revoking on a FREE read would act destructively on exactly the default value the bullet above exists to distrust. What changes instead is what the settings row *says*: `SettingsUiState.driveSyncBlockedByPlan` is `driveConnected && statusResolved && !SubscriptionGate.isPremium(status, complimentary)`, and the row reads "Connected — upgrade to resume uploads" rather than the bare "Connected" it showed indefinitely above "Free plan". The `statusResolved` term is load-bearing and not belt-and-braces: without it every launch would tell a paying subscriber their account was unusable for as long as billing took to answer. The premium rule itself lives once, as the pure `SubscriptionGate.isPremium(status, complimentary)` — a second copy inlined in the view model is how the gate and the UI drift apart. Note the grant is still *reported* as connected, so Disconnect stays on the row; "Not connected" next to a Disconnect button is the same contradiction the other way round. The **stored upload mode** is the screen's other standing claim that uploads are happening and is kept for the same reason, so it gets its own `cloudUploadBlockedByPlan` — deliberately *without* the `driveConnected` term, since a mode chosen before any account was connected still reads "Always on" — and the options are dimmed and annotated rather than disabled, because a tap is what raises the upgrade offer. While the plan is the blocker the row also **suppresses the reconnect prompt and the storage-full message, and the Connect button with them** — `showDriveReauthPrompt` / `showDriveStorageFull` carry that precedence, computed in the view model rather than the composable so it is testable at all (nothing can reach a private composable's branches cheaply, and `CloudSyncManager`'s latches are private and set only inside a tick). `CloudSyncManager` latches those two and clears them on a tick the gate allows, on `stopSync()` or on `onAuthorizationRestored()` — none of which happens while the gate refuses every tick — so a 401 or a full Drive from before the lapse would otherwise sit there permanently, offering a second and wrong reason for the same stopped uploads, with a Connect button next to a row reading "Connected". They are in-memory: if still latched in the same process they reappear on upgrade, when reconnecting can actually help; a restart drops them and a real failure re-latches them. What is **not** covered: while `statusResolved` is still false (Play never answers — offline, no Play Services, the resolve ladder exhausted) the row falls back to the confident "Connected", and the subscription card above it acts on the unresolved FREE default, so the original juxtaposition is still reachable in that window; entitlement is also resolved once per process and never re-queried, so an out-of-app re-subscribe does not refresh either. Both are [#87](https://github.com/jacoelt/backrecorder/issues/87) and [#88](https://github.com/jacoelt/backrecorder/issues/88).
- **Drive auth:** `DriveAuthManager` owns the OAuth grant via the Play Services Authorization API (`Identity.getAuthorizationClient`). `GoogleSignIn`/`GoogleAccountCredential` are **not** available — removed in play-services-auth 22 — so don't reach for them. It caches the access token for 45 min, re-authorizes silently, and force-refreshes on 401. `grantGeneration` changes whenever the grant does; anything caching account-scoped Drive state (folder ids) must compare it rather than rely on callers to invalidate. A grant that succeeds does **not** prove the app can reach Drive: the authorization is made by Play Services under its own uid, so a per-app firewall (NetGuard was the whole of #107) leaves Settings reading "Connected" while every REST call from this app stalls at connect — the first trace is the identity lookup timing out, followed by the sync loop's `Sync error` lines once its gates pass.
- **Nothing slow may be *awaited* under `sessionMutex` (#102):** `authorize()` runs its whole body under that lock, and the account check inside it makes a Drive `about.get` — so every other grant operation queues behind a network call. That is how the Settings screen's `init`-time `restoreSession()` made the Connect button look dead: google-http-client's 20 s default applies **per resolved address**, not per request, so one blackholed connect to googleapis.com held the lock for **320 s**, the user's tap suspended on `withLock` drawing nothing, and the tap's own lookup then burned another 320 s — about eight minutes from tap to any visible consequence, with no log on a release build (`-assumenosideeffects` strips `Log.d`/`Log.i`, and the waiting path logs nothing anyway). The lookup is now bounded by `IDENTITY_LOOKUP_TIMEOUT_MS` and, crucially, **abandoned rather than cancelled**: it is `async`-ed onto the `@ApplicationScope` and *awaited* under `withTimeout`, because the resolver ends in a blocking `execute()` on a socket that no cancellation can cut short — a `withTimeout` wrapped around the call itself would not return until the call did, which is the same constraint `SavedRecordingUploader` documents. What stops is this coroutine's *wait*, which is what holds the lock. The Play Services call in the same `withLock` carries its own `PLAY_SERVICES_TIMEOUT_MS` for the identical reason — bounding one slow call under a lock and leaving the other unbounded fixes nothing — and *that* one is a genuinely cancellable `Task`, so its bound aborts the call rather than abandoning it; the `TimeoutCancellationException` arm must come before the `CancellationException` arm, since a timeout is one. The abandoned lookup is still **watched for its answer**, because discarding it outright would have *weakened* the account pin rather than left it alone: a lookup that never answers pins nothing, an unpinned session omits `setAccount` from every later request — the drift guard itself — and before the bound existed a slow network still pinned, because the caller waited however long it took. So `pinWhateverTheOrphanResolves` records the pin late, under the lock, guarded on nothing being pinned yet **and on `cachedToken` still being the token the lookup asked about** — not on the grant generation, which the adoption this lookup belongs to bumps itself; an access token belongs to one grant for one account, and every teardown nulls it, so an unchanged token means an unchanged account. That token is read `@Volatile` rather than under `tokenMutex`, because taking that lock inside `sessionMutex` would park a Connect or Disconnect tap behind a refresh for the full Play Services bound. The watcher's body is wrapped, like every other `@ApplicationScope` launch here, because that scope has a `SupervisorJob` and no handler and the pin write is a DataStore write that throws. One abandoned lookup is cheap and a stack of them is not, so since #104 the lookup is **single-flighted by token** (`sharedLookupFor`): an abandoned lookup is still running and still holds a `Dispatchers.IO` thread, a throwaway Drive client and a pending socket for that whole 320 s, and the callers reaching it repeat freely — a Settings entry, an app launch, a Connect tap — so ten trips through Settings used to park ten of that pool's 64 slots, in the pool Room, DataStore, the sync loop and `SavedRecordingUploader` share. Four things about the shape. The key is the **token**, not the manager, because a token from another grant has another account behind it and answering for it from the first lookup is exactly the drift the check exists to catch; the saving therefore rests on Play Services handing back one access token for a live grant, and lookups for *distinct* tokens still stack one orphan each, which is [#117](https://github.com/jacoelt/backrecorder/issues/117). Only *outstanding* lookups are shared, never their answers — a completed one is dropped rather than cached, so no verdict can be read back under a later grant. What gets shared has usually been **abandoned** already (its first caller gave up at the bound while it kept running), so reuse is bounded by `LOOKUP_REUSE_WINDOW_MS` rather than by the orphan's own life: a window at the budget would reuse nothing at all, since a caller that waits out the bound holds `sessionMutex` for all of it and the next one therefore arrives a whole budget later — but an unbounded one would leave a network that recovered mid-stall rejoining the dead socket for the orphan's whole ~320 s, resolving "unknown" and pinning nothing meanwhile. A minute is a judgement between those two, not a measurement. Past it an adoption asks again on a fresh socket, and the orphan is still left running rather than cancelled. **Skipping** the lookup once `pinnedAccountId` is set is not the fix either: that lookup is the detection half of the pin, and skipping it removes the backstop. The map is guarded by `sessionMutex` (every path reaches it under `adoptLocked`), and an entry is dropped **when its lookup answers** (`dropAnsweredLookup`), by whichever side received the answer — the caller that waited it out, or the late-pin watcher when the answer came after the bound — rather than at teardown: on the network this is written for, the lookup is still outstanding when the user gives up and leaves, and the answer carrying an account's address and id (a stranger's where the pin refused the grant) lands minutes later, with no further adoption coming to prune it. Teardown deliberately leaves an *outstanding* entry alone, since dropping it cannot stop the orphan that holds all of it anyway and would let a disconnect-reconnect cycle stack the very lookup this map prevents. Note the bound also sets a named worst case for `SavedRecordingUploader`: a refresh inside the request initializer can now spend 30 s before any socket exists, which google-http-client's own timeouts do not cover. A bound is also not enough on its own: the tap must *show* the wait, so `SettingsViewModel.driveConnecting` renders the Connect affordance as a `BusyButton`, and every path the *user* can start a grant from — Connect, an upload-mode change, and the consent result — goes through the one `claimingDriveConnect` guard (the ungated `restoreSession()` in the screen's `init` and in `resumeCloudSync()` stay outside it, and a tap that queues behind one of those now renders the spinner rather than nothing). Not just to discard a second tap: two grant operations at once publish two `_consentRequest`s, and the screen launches the second consent sheet over the first.
- **The claim spans the consent round trip (#105):** `claimingDriveConnect`'s `finally` cannot cover the consent path, because `requestDriveAccess()` *returns* as soon as it publishes the `PendingIntent` and the screen launches the sheet a frame or two later, from a `LaunchedEffect`. Releasing there left the Connect button live in between, and a tap landing in that window started a second `authorize()` that took the claim — so the real `onConsentResult` was discarded and a grant **Google had already approved** was lost, silently and with no retry. The claim is therefore handed to `_awaitingConsent`, set *before* `_consentRequest` is published, and `driveConnecting` is the OR of the two (a `combine`/`stateIn(Eagerly)`, as `upgradeBusy` is and for the same stale-`value` reason). `onConsentResult` passes `continuesConsent = true`: it skips the `_awaitingConsent` guard because it **owns** that claim, while still refusing over a genuinely running call — the one case where an approved grant can still be dropped, so that refusal carries a `Log.w` rather than being silent. It is deliberately **not** conditional on the claim still being held: a process death during the sheet replaces the view model, and the restored launcher then delivers a real grant to a fresh instance that was never awaiting it, so a conditional guard would reintroduce the very loss this fixes. The claim is released **on the result, never at launch**. Releasing it in `onConsentLaunched()` was tried and is wrong: the settings window keeps focus for the hundreds of milliseconds the consent activity takes to appear, so the Connect button goes live again while the first sheet is still opening, and a second tap — likely, from someone who has just watched a dead-looking button for several seconds — publishes a second request that the still-composed `LaunchedEffect` opens *over* the first. The leak this shape must not have — a claim outliving a consent flow that never returns, which is a permanently disabled Connect button and so the #102 defect in a new place — is therefore not closed by a cleanup hook but by three standing properties: `_awaitingConsent` is only ever set *together with* `_consentRequest`; while that request is live, any composition of the settings screen launches it, and `ActivityResultRegistry` answers a launch even when the intent sender is dead, so a result always arrives; and the view model dies with the settings back-stack entry, so leaving outright ends the claim too. `onScreenLeft()` deliberately does **not** drop the consent request or its claim, unlike every other dialog it clears — see below for why that would be destructive. What must **not** be added here is a generation counter dropping a request published after the screen left. It looks like the #74 fix for a stray dialog and it was tried; it is wrong, because `DriveAuthManager.authorize()` calls `clearLocked()` *before* it reports `ConsentRequired`. By the time that outcome exists the session is already torn down, so the `PendingIntent` is not a stale artifact — it is the only route back to a working account. Dropping it disconnects Drive **silently**: no sheet, no error, uploads simply stopped, which is a worse version of the lost grant this issue exists to prevent. The late publish is kept deliberately and picked up by the next composition.
- **Drive seams:** `DriveAuthManager` reaches Play Services through `DriveAuthorizationClient` and builds its REST client through `DriveServiceFactory`; `di/CloudModule` binds both, and instrumented tests replace just that module via `@TestInstallIn(replaces = [CloudModule::class])` — `FakeDriveAuthorizationClient` (no grant until `grantAccess()`, a new token per call) plus a factory aimed at `FakeDriveServer`, an in-process Drive v3 stand-in. The real Drive client, grant state machine and folder logic all still run. Cleartext to the loopback fake is allowed by a **debug-only** network-security config in `app/src/debug`; the release build is untouched, so only `assembleRelease` proves the reflective client's ProGuard keep rules.
- **Drive folder layout:** `BackRecorder/staging` holds segments; `recovery_<timestamp>` folders are siblings under `BackRecorder/`, never inside `staging`. Anything inside `staging` is deleted once it ages past the 24h buffer, so a recovery folder placed there takes its contents with it. Saved recordings (#84) go in `BackRecorder/` itself, for the same reason — they are the copy the user means to keep, and staging's eviction would destroy it a day later. Nothing the user is meant to keep may ever be written inside `staging`.
- **The saved-recording Drive copy (#84):** saving a recording writes it to the SAF destination the user picked and *also* uploads a copy to `BackRecorder/`. The local file is the product and the copy is a bonus, which is what every decision in `SavedRecordingUploader` follows from. Two deliberate readings of the agreed criteria, which said "Drive connection active and subscription enabled" and "a toast": **`CloudUploadMode` is part of the gate too**, because sending a copy over cellular for someone who chose Wi-Fi-only — or at all for someone who chose OFF — would contradict a setting they already gave us; and the in-app half of a failure is the app's existing **snackbar**, which is how every other message on that screen is shown and which only appears while the main screen is composed (what the notification is for). `enqueue` **does not suspend** and is called from `SaveRecordingUseCase.deliver` after `copyToUri`, inside a `try`/`catch` that cannot fail the save — a save reported as failed because a backup could not be queued would be strictly worse than no backup. It **takes the file over by `renameTo`**, because the save deletes its temporaries in a `finally` the instant `execute` returns and would otherwise pull the file out from under an upload still reading it; everything after the hand-off must treat that file as gone. All gating happens on the `@ApplicationScope` afterwards, never at the call site: mode is not `OFF`, the user is premium, Drive is initialized, and the transport satisfies the mode (`isCloudNetworkAvailable`, shared with the sync loop so the two cannot disagree about what Wi-Fi-only means). It **waits** for `statusResolved` rather than refusing on it — unlike the sync loop it is not on a schedule, and billing usually has not answered at the moment of a save, so refusing would deny a paying subscriber the copy because Play was slow. A `Mutex` keeps **exactly one transfer on the wire** at a time — several saves would otherwise each push a full file through the one Drive client, which is what `CloudSyncManager`'s per-tick cap exists to prevent. It wraps the transfer and the dedupe probe in front of it (#92) *and nothing else*: the preconditions, and above all the `statusResolved` wait, sit outside it, because a lock held across that wait made several saves queue 30 seconds **each, serially**, for an answer they would all have taken from the same shared flow. The backoff is outside it too, for the same reason. What bounds an attempt is **google-http-client's own 20s connect / 20s read defaults** — not the `withTimeout` around it, which cannot interrupt a blocking `execute()` and only fires once the call returns on its own (it is a backstop for a transfer that trickles just fast enough never to trip the socket timeout). Leave those defaults alone: the read timeout is per socket read rather than per transfer, so a large upload still making progress never trips it, and widening them only weakens the one thing stopping a half-open socket from holding the upload lock, and every save behind it, indefinitely. Three attempts, and a `HttpResponseException` is classified rather than blindly retried: auth and quota are **terminal** (neither a revoked grant nor a full account is fixed by asking again two seconds later), while a throttle is retried after a *much* longer wait — it is genuinely transient, and unlike the sync loop there is no later tick to pick it up. Those predicates live in `DriveErrorClassification`, shared with `CloudSyncManager`, for the same reason the network check is: two copies would eventually disagree about which 403 means what. **Every attempt after the first, and once more before the user is told it failed, first asks `DriveCloudStorage.findSavedRecording` whether an earlier attempt landed anyway (#92)**, a match returning success without transferring again. A connection dropping *after* Drive commits the bytes fails the attempt while the file exists there, and Drive does not dedupe by name, so a blind retry left two or three copies of one recording on the user's quota. A resumable upload is **not** the fix it looks like: the client cannot resume a session across a new `execute()`, so a dropped one is abandoned and the retry opens a fresh session — the same duplicate. The probe before `reportFailure` is the one that is easy to drop and shouldn't be: the last attempt fails the same way, and it is the only path that tells the user their backup failed while the copy sits in `BackRecorder/`. Each run stamps a **UUID of its own into the file's `appProperties` as it creates it** and asks for that, so the question has exactly one right answer. Identifying the copy by what it looks like instead — name and byte length — cannot be made safe, and that is the non-obvious part: the name is whatever the user typed in the picker and is freely repeatable, and size discriminates far less than it appears to, because the app records at a fixed 32 kbps and its selections are minute-quantised, so two different recordings of equal duration plausibly share a byte length. Matching one of those reports an unrelated recording's copy as this one's backup and drops it silently, which is strictly worse than the duplicate being prevented. A `createdTime` bound narrows that but cannot close it: it weighs the device's clock against Drive's, and two saves running concurrently still overlap. `appProperties` is app-private and searchable under the narrow `drive.file` scope already in use. The probe answering null — a `files.list` lagging a fresh commit, a probe that throws — costs a duplicate and never the copy, which is the bonus-copy principle again; losing the transport mid-run skips the probe entirely, because with no network the request cannot answer and a doomed one holds the lock, and every save behind it, for the whole connect timeout before the user hears anything. Both probe sites take `uploadMutex` (the in-attempt one with the transfer, the pre-report one on its own) and neither needs a `withTimeout`: one small metadata response under the same socket bounds has no trickle for a backstop to catch. Between attempts the mode and transport are re-read, and the two are **not** treated alike — turning uploads off is the user declining the copy, so the run ends silently, while losing the transport is not a decision they made and is still reported. The same split governs the up-front check, which is three-way (`Eligibility`) rather than a boolean, and it turns on whether the user lost something they were promised. Uploads off, no entitlement, billing never answering, **and no Drive grant** are all `DECLINED` and silent to the user — though the last two, which the user did not choose, leave a `Log.w` line (#107) so a release build can still say why no copy appeared. That last one is the non-obvious member: an upload mode other than OFF does *not* imply a connected account, because `SettingsViewModel` writes the mode before asking for consent and leaves it set when the user backs out of the sheet — so mode-on-with-no-grant is a normal, persistent state, and reporting it would mean a failure notification on every save, forever, for a copy the user never granted access for. The grant is **awaited** (bounded) rather than read once, for the same reason billing is: it is restored asynchronously at launch, so a connected user saving in that window would otherwise read as having no grant and lose the copy with nothing to retry it. Both bounded waits end in a silent decline — a paying subscriber whose Play or Drive state never resolves loses the copy quietly, which is the deliberate trade against reporting a failure to someone whose setup may simply be incomplete. Being **offline** is `BLOCKED` and reported: there the setup is complete and the expected backup genuinely did not happen, and since the identical condition found one attempt later was already reported, staying silent made the commonest version of it the invisible one. The report is two halves: the in-app message goes out first and unconditionally, and the notification — which can fail on permission or a dead channel — is wrapped so it cannot take the message with it and leave a failed upload completely silent. The in-app half is an **unlimited `Channel`, not a `StateFlow`** — the same reasoning as `FlushCoordinator`: a channel buffers with no receiver, so a failure raised while the user is in Settings is delivered when they come back, and because each send is an event rather than a value, two failures carrying the *same* text are both reported. `MainViewModel` shows them one at a time, waiting for each to be dismissed before taking the next, and stamps each with an id (`UploadError`) that `MainScreen` keys its `LaunchedEffect` on. That id is not decoration: keyed on the text alone, two failures naming the same recording are indistinguishable to Compose — the dismissal and the next message both land before it recomposes, the effect never re-runs, and the collector waiting on that dismissal parks forever, withholding every later failure. It is the conflation the channel removed, reappearing one layer up. The notification carries its own id per failure and a group key, so a batch neither collapses into one naming only the last nor stacks unbundled. **Neither half is guaranteed**, and they cover different absences rather than backing each other up: `notify` drops silently when POST_NOTIFICATIONS was never granted (this app only asks for it in the start-recording flow), and the in-app message needs a main screen to show it — a view model cleared while a failure is on screen consumes that one without redelivery. The `try`/`catch` around the notification is only for an unexpected throw out of the builder or the service, not for a denied permission, which does not throw. The notification goes through the `UploadFailureNotifier` seam, posts on the **cloud-sync channel**, and is `VISIBILITY_PRIVATE` with a `publicVersion` carrying only the generic title — this app exists to record discreetly, and the recording's name on a lock screen defeats that. The seam is bound in `AppModule` rather than `CloudModule` (which instrumented tests replace wholesale), because `NotificationCompat.build()` reaches the platform builder and throws on the JVM, which would otherwise make "the user was actually told" the one thing no unit test could assert. The display name is read from the SAF provider, then **bounded and stripped of anything but letters, digits and a little punctuation** before it reaches Drive metadata or a notification: it comes from a content provider that may not be ours.
- **Targeting API 36 (#69):** `compileSdk` and `targetSdk` are both 36, which Play requires, and several platform behaviours follow from that number rather than from anything in the code. Edge-to-edge is **enforced** — `windowOptOutEdgeToEdgeEnforcement` is ignored, so the system bars are always drawn behind the app and only the icon tint (`isAppearanceLightStatusBars`, in `BackRecorderTheme`) is still ours. `Window.setStatusBarColor` is a deprecated no-op **only on API 35+** — below 35 it is still honoured, so `BackRecorderTheme` must not call it: the write would repaint the bar opaque over the transparent one `enableEdgeToEdge()` sets in `MainActivity.onCreate`, and the bar would then look different on API 26-34 than on 35+. Insets are taken in two places: both `Scaffold`s pass `contentWindowInsets = WindowInsets.safeDrawing` rather than the system-bars default, **and** both `TopAppBar`s pass a matching `windowInsets`, because `TopAppBarDefaults.windowInsets` is system-bars-only and the bar would otherwise sit under a landscape display cutout while the body below it cleared one. **Where the content scrolls under a collapsing bar, that padding goes *inside* the scroll container (#71):** `MainScreen` pairs `TopAppBarDefaults.enterAlwaysScrollBehavior()` with a `verticalScroll` `Column`, and in material3 1.4.0 `Scaffold` reports `top = topBarPlaceable.height` while `TopAppBarLayout` measures itself at `maxLayoutHeight + heightOffset` — the bar genuinely shrinks rather than sliding, so that padding changes on every frame of a drag, and outside the scroll it resizes the viewport mid-gesture instead of translating the content. Inside, it is content, which is what the idiomatic `LazyColumn` form expresses as `contentPadding`. `SettingsScreen` keeps the padding outside on purpose: with no `scrollBehavior` its padding is constant, so there is nothing to move. The ordering is **not** visible to Compose's semantics tree the way a reader expects, but it is assertable: a semantics node reports the bounds of the coordinator its own modifier sits at (`SemanticsNode.findCoordinatorToGetBounds`), so the scroll node's bounds *are* the viewport, and `MainScreenInsetsTest` pins them to the whole window. Back is delivered through `OnBackInvokedCallback` only **on Android 16+ devices** — there `onBackPressed()` is not called and `KEYCODE_BACK` is not dispatched (an older device running this target still dispatches both) — so back navigation works purely because `android:enableOnBackInvokedCallback="true"` lets AndroidX `OnBackPressedDispatcher` (and so Navigation Compose) register; it is declared on `MainActivity` rather than left to a default: `false` is still a documented opt-out at this target, so the attribute is read, and the platform docs do not state what it defaults to at a given `targetSdk` — do not rely on that. And `screenOrientation` / `resizableActivity` / aspect-ratio restrictions are ignored on displays at or above sw600dp, so landscape and activity re-creation are unavoidable there; nothing in the manifest tries to restrict them, and anything that would must instead survive re-creation.
- **Notifications:** Three channels — recording, cloud sync, recovery — all created by `NotificationChannels.createAll()`. Instrumented tests must call it themselves: `HiltTestApplication` replaces `BackRecorderApp`, and a foreground service posting to a channel that doesn't exist kills the process with `CannotPostForegroundServiceNotificationException`.
- **Instrumented tests:** `testInstrumentationRunner` is `com.backrecorderapp.HiltTestRunner`, which swaps in `HiltTestApplication` — the real `BackRecorderApp` connects billing and resumes cloud sync on create, which no test should do. Compose UI tests use `@HiltAndroidTest` + `HiltAndroidRule` + `createAndroidComposeRule<MainActivity>()`; `ComposeHarnessSmokeTest` is the reference. Seed preferences in a rule ordered *between* the cleanup rule and the compose rule, not in `@Before` — the compose rule launches the activity before `@Before` runs, and `NavGraph` fixes its start destination from `disclaimerAccepted` on first composition. CI runs them in the `Instrumented tests` job of `.github/workflows/ci.yml`, on a hosted emulator with a cached AVD; locally they need an emulator or device (`./gradlew :app:connectedDebugAndroidTest`). The `main: PR + green CI` ruleset now **requires** that check alongside `Build and test`, with no bypass actors — so a flaky instrumented test makes every PR unmergeable with no admin override, and test stability here is a production concern for the repository itself.
- **Shared instrumented harness:** `androidTest/.../testing/InstrumentedTestSupport.kt` owns what every flow test repeats — `awaitUntil` and the `RecordingService`/recorder waits built on it, `clearRecordedState(segmentDao)`, `createNotificationChannels()`, `PreferenceSnapshot` (capture a preference before seeding, `restoreAll()` on the way out) and `cleanUpRule(hiltRule) { … }`. **Seeding stays in each test** — that is the part that genuinely differs. Rules go in this relative order (the `order` numbers are whatever makes that come out, since not every test has all of them): the Hilt rule, then `GrantPermissionRule` where a granted start is wanted, then `cleanUpRule`, then the test's own seeding, then the compose rule if there is one — `DriveSyncE2eTest` and `RecordingSegmentTest` drive `ActivityScenario` themselves and have none. Cleanup must sit *outside* seeding, never in the same rule and never in an `@After`: `ExternalResource` skips its own `after()` when its `before()` threw, so a seeding failure would otherwise leave rows, cache files and flipped preferences for the next test in the shared process. `cleanUpRule`'s `before()` is also where `hiltRule.inject()` happens, so seeding below it can use the injected fields. `FakeAudioRecorderFactory` also carries two hooks for driving failure and timing, both reset by `reset()`: `failNextStart()` makes one segment's recorder refuse to open, and `holdStarts()` parks every later recorder inside `start()` until its latch is counted down — which is what turns "teardown landed mid-rotation" from a race a test can only hope to hit into a deterministic one. Release a held latch in a `finally`, or the service never stops and the cleanup rule hangs. Note that a test which stops the service within milliseconds of starting it is killed by the framework with `ForegroundServiceDidNotStartInTimeException` before any assertion runs — let a segment open first.
- **Instrumented test isolation:** `androidTest` runs under the **AndroidX Test Orchestrator** with `clearPackageData=true` (`app/build.gradle.kts`), so every test gets its own process and a `pm clear` of the app and test packages — fresh DataStore, Room database, cache dir, notification channels and **revoked runtime permissions**. Don't turn this off: runtime grants are package-wide and permanent for an instrumentation run, so `RecordingSegmentTest`'s `GrantPermissionRule` would otherwise leak `RECORD_AUDIO` into every later class and make a denied-permission test pass vacuously. Still seed the state a test depends on explicitly rather than relying on the clear. Note a bare `adb shell am instrument` bypasses the orchestrator entirely — use `./gradlew :app:connectedDebugAndroidTest`.
- **Runtime permissions in tests:** two platform behaviours constrain every test here. Revoking a permission in-process SIGKILLs the app's processes, which under instrumentation is the test run itself; and granting `RECORD_AUDIO` through the dialog to an already-running app does the same. So: **`GrantPermissionRule` for granted paths, UI Automator for denied paths** — the dialogs are system UI, outside Compose's semantics tree, and `SystemPermissionDialog` (deny-only, by design) reaches them. A test depending on an un-granted start asserts that precondition. `FirstLaunchFlowTest` covers the granted path, `FirstLaunchPermissionDeniedTest` the declined one (it is what proves both permissions are requested), and `ReturningLaunchFlowTest` the already-accepted launch.
- **`BootReceiver` and Hilt:** `BootReceiver` resolves `AppPreferences` through `EntryPointAccessors`, **not** `@AndroidEntryPoint`. Under instrumentation `HiltTestApplication`'s component is built by `HiltAndroidRule`, so a manifest-registered `@AndroidEntryPoint` receiver that catches `BOOT_COMPLETED` before the first test aborts the whole run. Any new manifest-registered receiver needs the same treatment.
